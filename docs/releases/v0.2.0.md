# Open Cricket v0.2.0

Open Cricket v0.2.0 makes single-token answer-code scoring the default, reducing
each question to one model pass while returning the original category labels.
It also accelerates full-label scoring through batched trie evaluation and
avoids unused vocabulary calculations on supported MLX Qwen2 models.

This release changes classification behavior by default. Request and response
schemas remain unchanged, but predictions, probabilities, and confidence values
can differ from v0.1.0.

## New default: answer codes

`LocalClient`, `classify`, `as_runnable`, the CLI, and the default HTTP service now
use `mode="answer_codes"`. Categories receive A–Z codes in their supplied order.
The model scores all candidate codes in one forward pass; responses retain the
original labels and the existing Choice, Score, and Noul formats.

- Each code must encode as one distinct token. Unsupported tokenization fails
  explicitly.
- Up to **26 options per question** are supported in this mode. Larger candidate
  sets raise an error; they are not truncated or silently switched to another mode.
- Only the first code token is scored. Quotes, label tokens, and EOS are excluded
  from the scored event. Probabilities remain relative to the supplied candidates.
- Local scoring still generates no output text, so `usage.output_tokens` is zero.
- The server now accepts `OPEN_CRICKET_MODE` to select `answer_codes`, `sequence`,
  or `constrained` at startup.

The default checkpoint remains `Qwen/Qwen2.5-1.5B-Instruct`. Python 3.10+ and the
existing optional runtime dependency ranges are unchanged.

## Upgrading from v0.1.0

Existing request bodies and response parsing continue to work. Applications
using more than 26 Choice labels must select label scoring; the wire schema
continues to allow up to 255 labels.

To retain v0.1.0's full-label scoring semantics, set the mode explicitly:

```python
from open_cricket import LocalClient

client = LocalClient(mode="sequence")
```

Pass the same `mode="sequence"` argument to `classify` or `as_runnable` when
using those entry points. For the CLI:

```bash
open-cricket --input examples/support.json --mode sequence
```

For the server, set this variable and restart the process:

```bash
export OPEN_CRICKET_MODE=sequence
```

An existing explicit mode selection takes precedence over the new default.
`constrained` scoring remains available. The synthetic `--demo` and low-level
`score_paths` function retain their sequence-scoring default.

Answer-code assignment and candidate order can affect predictions. Re-evaluate
application examples and confidence thresholds when adopting the new default;
code-token probabilities are not interchangeable with completed-label
likelihoods. Selecting `sequence` retains the scoring definition, but runtime
optimizations can still produce floating-point differences.

## Performance

Measured warmed median times with `Qwen/Qwen2.5-1.5B-Instruct`, excluding model
loading, on 12 synthetic routing cases in two candidate orders and three timed
repeats per case/order:

| Runtime | Full-label scoring in v0.2.0 | Default answer codes | Speedup |
| --- | ---: | ---: | ---: |
| MLX, Metal | 79 ms | 46 ms | 1.72× |
| Hugging Face, Apple MPS | 143 ms | 58 ms | 2.45× |

These compare modes within v0.2.0, not end-to-end timings against v0.1.0.
Both runtimes returned the expected label in 24/24 code evaluations versus
22/24 label evaluations. The cases also informed prompt development: this is a
smoke evaluation, not independent evidence of general accuracy. Individual
candidate probabilities changed by as much as 0.84. Results depend on workload,
model, hardware, and precision; CUDA was not benchmarked.

Full-label scoring also receives these improvements:

- **Batched trie evaluation:** deterministic token stretches are scored together,
  up to 16 positions per forward pass. All original token probabilities and EOS
  scoring are retained. Enabled for MLX and Hugging Face GPU inference; HF CPU
  keeps serial cached scoring because batching slowed the measured workload.
- **Selective MLX vocabulary projection:** the exact MLX-LM 0.28 Qwen2 model
  class projects only scored hidden states. Tied embeddings, separate heads, and
  their quantized forms are supported; other model classes use their normal path.
  This reduced measured 1.5B latency from 86 to 83 ms on a 112-token prompt and
  from 197 to 179 ms on a synthetic 546-token prompt, versus chain scoring alone.

Label-scoring arithmetic is mathematically equivalent, but lower-precision
execution can shift probabilities and close rankings. See the
[detailed benchmark results](../../README.md#measured-performance).

## Compatibility and verification

The original three-method token-backend protocol remains supported. An optional
`score_chain(requests)` callback enables batched evaluation. `model_calls` still
counts scored trie nodes, not physical forward passes; answer-code scoring
reports one node per question.

Development validation passed all **50 tests**, including real miniature HF/MLX
models, quantized MLX projection, cache isolation and rollback, answer-code
tokenization, and SDK/CLI/HTTP/LangChain integration. Optional runtime tests
require their dependencies and suitable hardware; the default CI suite skips them.

Reproduce the answer-code evaluation from the checkout with the relevant runtime
installed:

```bash
uv run python examples/benchmark_answer_codes.py --backend mlx --repeats 3
uv run python examples/benchmark_answer_codes.py --device mps --repeats 3
```

The expanded [backend benchmark](../../examples/benchmark_backend.py) compares
uncached, cached, chain-scored, and fully optimized label scoring. It accepts
`--chain-scoring on|off` and `--message-repeats` for controlled comparisons.

See the [SDK guide](../sdk.md), [server configuration](../server.md#configuration),
and [scoring reference](../technical/scoring.md) for usage details.
