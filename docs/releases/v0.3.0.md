# Open Cricket v0.3.0

Open Cricket v0.3.0 removes the fixed local Choice candidate limit, makes answer
codes case-insensitive, and accelerates requests containing several questions on
the Hugging Face GPU backend. Existing request and response shapes continue to
work, but local `answer_codes` probabilities can change from v0.2.0.

## Case-insensitive, extensible answer codes

Local `answer_codes` mode now assigns canonical codes from `A–Z`, then `0–9`.
Letter case is treated as an output alias: for code `A`, the model probability of
both `A` and `a` contributes to the same candidate. Open Cricket combines alias
mass before applying temperature and normalizing across candidates, then returns
the original category label and canonical uppercase code.

After the 36 base codes are exhausted, Open Cricket introduces longer codes such
as `AA`, `AB`, and eventually `AAA`. It scores every case variant of a code—for
example `AB`, `Ab`, `aB`, and `ab`—as the same candidate. Code strings are
tokenized and checked for the active model; no model-specific token list is baked
into the package.

There is no fixed local Choice candidate count in v0.3.0. The previous 26-option
`answer_codes` limit and 255-label local wire-schema limit are removed. Model
context, memory, tokenizer compatibility, and request cost remain practical
limits. Third-party clients may retain their own schema limits.

When every case alias is one token, Open Cricket keeps the fast single-forward
path and does not score EOS. If any alias needs multiple tokens, every alias is
scored as a complete path including EOS. This distinguishes overlapping codes
such as `A` and `AA` and uses the existing request-local trie cache.

## Faster multi-question requests

The Hugging Face GPU backend now batches questions that use single-token answer
codes. It finds their exact shared token prefix, prefills that prefix once, and
batches the remaining question suffixes while preserving request order and the
public response contract.

- Single-question requests retain the direct path.
- Batches are bounded to 32 rows and 32,768 padded suffix tokens.
- CPU inference remains sequential because batching regressed the measured small
  workloads.
- MLX, custom backends, full-label modes, and requests containing multi-token
  code paths retain their existing execution paths.
- `usage.input_tokens` retains its logical sum-of-question-prompts definition;
  it does not report reduced physical computation.

## Performance

The final v0.3.0 scoring behavior was measured with
`Qwen/Qwen2.5-1.5B-Instruct`, float32, PyTorch 2.14.0, Transformers 4.57.6, and
Apple MPS. The benchmark compares independent per-question forwards with the new
shared-prefix batch path. Times are warmed medians over seven repeats; model
loading, HTTP transport, queues, and concurrent traffic are excluded.

| Four-choice questions | Sequential | Shared-prefix batch | Speedup |
| ---: | ---: | ---: | ---: |
| 1 | 60 ms | 60 ms | 1.00× |
| 4 | 238 ms | 133 ms | 1.79× |
| 16 | 957 ms | 335 ms | 2.86× |

The benchmark verifies that sequential and batched execution return the same
candidate probabilities within reported floating-point tolerance. Single-question
requests deliberately use the direct path, so their measurements should be equal
apart from ordinary timing noise. The maximum absolute probability difference was
0 for one question, 0.000000015 for four, and 0.00000349 for sixteen.

The performance benefit does not extend unchanged to very large candidate sets.
Once multi-token aliases are introduced, cached trie traversal adds model work,
and the number of case variants grows with code length. Benchmark representative
candidate counts on the intended model and hardware before setting service limits.

## Upgrading from v0.2.0

No request-body or public response-envelope changes are required. The default
mode remains `answer_codes`, and `sequence` and `constrained` remain available.

Re-evaluate predictions and thresholds when upgrading. Even with 26 or fewer
candidates, v0.3.0 combines uppercase and lowercase output mass whereas v0.2.0
scored only the canonical uppercase token. Candidate order can still affect model
predictions. Adding enough candidates to require a multi-token alias switches the
entire question from first-token scoring to completed-code-plus-EOS scoring, so
probabilities are not continuous across that boundary.

To retain completed-label scoring rather than answer-code scoring:

```python
from open_cricket import LocalClient

client = LocalClient(mode="sequence")
```

Use `--mode sequence` in the CLI or `OPEN_CRICKET_MODE=sequence` for the server.

Low-level answer-code results now include the canonical `code`, the most probable
`matched_alias`, and an `aliases` list containing token-level diagnostics for each
case variant. Typed SDK and HTTP responses continue to expose probabilities under
the original criterion labels.

## Compatibility and verification

The original three-method token-backend protocol remains supported. Optional
`score_chain(requests)` and `batch_next_logprobs(requests)` hooks enable cached
chain scoring and multi-question batching. Backends that normalize letter case to
the same token are handled without counting the duplicate alias twice.

Development validation passed all **61 tests**, including case-alias aggregation,
multi-token and overlapping codes, requests beyond 255 Choice labels, question
batching, cache rollback, real miniature HF/MLX models, and SDK/CLI/HTTP/LangChain
integration. A real Qwen2.5-1.5B MPS check confirmed that the reported `A`
log-likelihood equals `log(P(A) + P(a))` to floating-point precision and that all
four case variants of `AA` are included.

Reproduce the multi-question benchmark with:

```bash
uv run python examples/benchmark_questions.py --device mps
```

Results depend on model, prompt, candidate count, hardware, precision, and runtime
version; CUDA and concurrent server throughput were not benchmarked.

and [scoring reference](../technical/scoring.md) for the complete behavior.
